# TickPilot — Спецификация проекта (SPEC)

> Это **источник истины** по требованиям. Правила поведения агента — в `CLAUDE.md`.
> Порядок работ и промпты для запуска — в `PROMPT.md`.
> Если код противоречит SPEC — прав SPEC. Если SPEC противоречит реальному Minecraft API — прав API, а SPEC нужно обновить и записать это в «Журнал решений».

## 0. TL;DR

TickPilot — серверный Fabric-мод для Minecraft Java Edition 1.21.1 (Java 21), который **сначала измеряет** нагрузку тика, **потом объясняет** её причину человеку и **только затем осторожно** ограничивает необязательные задачи. Работает и на dedicated server, и в одиночной игре (integrated server). Клиентский HUD — опционально и не обязателен.

**Главный принцип:** измерить → объяснить → осторожно оптимизировать. Никогда не ломать игровую механику ради красивых цифр TPS.

### 1.1 Маппинги: Mojang Mappings (Mojmap), НЕ Yarn

**Решение зафиксировано в журнале §13 (запись #1).** Проект собирается на официальных
Mojang mappings (`mappings loom.officialMojangMappings()` в `build.gradle`), а не на Yarn.
Все имена классов/методов в этом документе и в коде — **Mojang-нейминг**
(`ResourceLocation`, `Minecraft`, `Level`, `ServerLevel`, `MinecraftServer`, ...).
Если где-то в тексте всплывёт Yarn-имя (`Identifier`, `MinecraftClient`, `World`) — это
ошибка документа, а не инструкция писать код под Yarn.

### 1.2 Версии зависимостей (проверять, НЕ угадывать)

Точные версии **обязательно** получить из живых источников перед написанием `gradle.properties`:

```bash
curl -s https://meta.fabricmc.net/v2/versions/loader/1.21.1 | head -c 400   # fabric loader
# Fabric API для 1.21.1: https://modrinth.com/mod/fabric-api/versions?g=1.21.1
# Готовый шаблон build.gradle (Mojmap по умолчанию): https://fabricmc.net/develop/template/
```

Yarn mappings **не используются** — соответствующую строку в `gradle.properties` добавлять не нужно.

Ориентировочные значения (могут быть устаревшими — сверить перед использованием!):
`minecraft_version=1.21.1`, `loader_version=0.19.x`, `fabric_version=0.116.x+1.21.1`, Loom `1.17-SNAPSHOT` или новее.

**Проверка имён реального Minecraft API — не по внешним сайтам, а по кэшу проекта:**
самый надёжный способ — распаковать `mappings.tiny` из
`~/.gradle/caches/fabric-loom/1.21.1/.../mappings.jar` (колонки `official / intermediary / named`,
`named` = Mojang-имена) и грепать по нему; это ровно те мапперы, с которыми реально
собирается проект. Альтернатива — `./gradlew genSources` и просмотр декомпилированных
исходников в IDE. Внешние сайты вроде mappings.dev/linkie ориентированы на Yarn и
здесь малополезны.

## 2. Глоссарий

| Термин | Определение |
|---|---|
| **TPS** | Ticks per second. Цель — 20. Не может быть выше 20 в ванильной логике. |
| **MSPT** | Milliseconds per tick — время одного тика. Бюджет ~50 мс. **Главная метрика проекта.** |
| **Server thread** | Главный поток `MinecraftServer`. Всё, что трогает мир, выполняется только здесь. |
| **Integrated server** | Сервер внутри клиента при игре в одиночном мире. |
| **Deferred task** | Задача, зарегистрированная через API TickPilot, которую разрешено перенести на следующий тик. |
| **Activity zone** | Режим объекта (FULL / REDUCED / FROZEN), вычисленный по расстоянию до ближайшего игрока. |
| **Load level** | Уровень нагрузки сервера: NORMAL / ELEVATED / HIGH / CRITICAL. |
| **Adaptive mode** | Политика агрессивности: STRICT / BALANCED / AGGRESSIVE. |

⚠️ **Важно не путать две оси:** `Adaptive mode` (насколько мод вообще имеет право вмешиваться, задаётся человеком) и `Load level` (насколько сейчас плохо, вычисляется автоматически). В исходном описании они были в одном списке — это ошибка, они независимы.

## 3. Non-goals (что мод НЕ делает)

Явный список, чтобы агент не «дорисовывал» лишнее:

- NG-1. Не переписывает и не заменяет тик-луп Minecraft целиком.
- NG-2. Не выполняет игровую логику асинхронно (не «async chunks», не «async entity ticking»).
- NG-3. Не обещает магический рост TPS и не пишет маркетинговых заявлений в README.
- NG-4. Не заменяет spark / Observable — он дополняет их и должен быть с ними сравним.
- NG-5. Не требует клиентского мода для работы на dedicated server.
- NG-6. Не трогает поведение других модов глобально без allowlist.
- NG-7. Не реализует GUI-редактор конфига в v1 (только файл + `/tickpilot reload`).

## 4. Инварианты безопасности (INV) — нарушение = баг блокирующего уровня

Эти правила важнее любой фичи. Их нельзя обойти «ради производительности».

- **INV-1 (Thread safety).** Запрещено обращаться к `Level`, `ServerLevel`, `Entity`, `BlockEntity`, `LevelChunk`, `MinecraftServer`, реестрам и игровым коллекциям из любого потока, кроме серверного. В фоне разрешены только чистые вычисления над скопированными примитивами/иммутабельными снимками.
- **INV-2 (Apply on main).** Любая мутация мира применяется на серверном потоке.
- **INV-3 (Safe by default).** Любая спорная оптимизация выключена по умолчанию и имеет отдельный флаг конфига.
- **INV-4 (No silent breakage).** Если безопасной точки интеграции нет — реализуется только профилирование, а в README/логе честно пишется об ограничении.
- **INV-5 (No global throttling).** Массовое ограничение entity/block entity допустимо только через явный allowlist.
- **INV-6 (No per-tick allocation storm).** Профилировщик не создаёт объекты на каждый тик/сущность в горячем пути. Только примитивы, ring buffer, переиспользуемые аккумуляторы.
- **INV-7 (No global mutable state).** Никакого `static` состояния, переживающего мир. Состояние привязано к конкретному `MinecraftServer` и уничтожается при остановке.
- **INV-8 (Player-critical never throttled).** Загрузка чанков для игрока, телепортация, force-loaded области и всё, что нужно игроку прямо сейчас, не ограничивается никогда.
- **INV-9 (Fail-safe).** Любая ошибка внутри TickPilot не должна ронять сервер: ловим, логируем один раз с cooldown, отключаем подсистему, продолжаем.
- **INV-10 (Overhead cap).** Собственный overhead мода в дефолтном режиме — не более ~1% MSPT; измеряется и выводится в `/tickpilot status`.

## 5. Функциональные требования (FR)

Каждое FR имеет критерий приёмки (AC). На эти ID нужно ссылаться в коммитах и тестах.

### FR-1. Измерение тика
Мод измеряет длительность каждого тика серверного потока и хранит историю в ring buffer.

**AC-1:** `TickMetrics` отдаёт: current TPS, avg MSPT (окно 5с / 1мин / 5мин), p95, p99, max MSPT, длительность последнего тика, uptime. Все значения обновляются без аллокаций в горячем пути.

**AC-1b (добавлено, журнал §13 запись #4):** если сервер заморожен (`/tick freeze`) или у него изменён целевой tickrate (`/tick rate`) через `MinecraftServer.tickRateManager()`, `status`/`explain` явно показывают это состояние и не трактуют пониженный TPS как признак перегрузки в этом случае. Собственный ring buffer TickMetrics — источник для p95/p99/окон; ванильные `MinecraftServer.getTickTimesNanos()`/`getAverageTickTimeNanos()` используются только как кросс-проверка в тестах, не как основной источник данных.

### FR-2. Профилирование по категориям
Разбивка времени тика по категориям: `TOTAL`, `ENTITIES`, `BLOCK_ENTITIES`, `SCHEDULED_TICKS`, `RANDOM_TICKS`, `CHUNK_OPS`, `SAVING`, `NETWORK`, `OTHER`.

**AC-2:** сумма категорий ≤ TOTAL; разница попадает в `OTHER`; категория добавляется только если для неё найдена безопасная точка внедрения. Недоступные категории показываются как `n/a`, а не как ноль.

### FR-3. Определение дорогих объектов
Агрегированная статистика по `EntityType`, `BlockEntityType`, dimension, mod ID (из namespace идентификатора), категории задач.

**AC-3:** `/tickpilot top entities` показывает top-N по суммарному времени за окно, с количеством экземпляров и средним временем на экземпляр. Координаты хранятся только во время активной сессии профилирования, в ограниченном top-N буфере, и очищаются при её завершении.

### FR-4. Sampling-профилировщик
Глубокое профилирование включается по команде на N секунд, а не работает постоянно.

**AC-4:** `/tickpilot profile 30` запускает сессию, `/tickpilot profile stop` останавливает досрочно; по завершении печатается отчёт; повторный запуск во время активной сессии возвращает понятную ошибку, а не крашит.

### FR-5. Бюджет тика и уровни нагрузки
`TickBudget` вычисляет `LoadLevel` из сглаженного MSPT.

Пороги вычисляются из `target_mspt` и `critical_mspt` (FR-15). Обозначим
`mid = target + (critical − target) × 0.5`.

| Load level | Условие (формула) | При дефолтах (40 / 50) |
|---|---|---|
| NORMAL | avgMspt < target | < 40 |
| ELEVATED | target ≤ avgMspt < mid | 40 … 45 |
| HIGH | mid ≤ avgMspt < critical | 45 … 50 |
| CRITICAL | avgMspt ≥ critical | ≥ 50 |

Порог HIGH задан **долей интервала** `target → critical`, а не приростом «target + 25 %»
(журнал §13, запись #7): при `target = 40`, `critical = 50` старая формула давала
`40 × 1.25 = 50 = critical`, то есть пустой недостижимый уровень HIGH. Формула через долю
интервала корректна при любых валидных `target < critical` из конфига.

**AC-5:** переход между уровнями имеет гистерезис (порог входа ≠ порогу выхода) и минимальное время удержания, чтобы не дребезжать каждый тик. Каждый переход логируется один раз.

### FR-6. Adaptive scheduler
Планировщик задач, зарегистрированных через публичный API TickPilot.

**AC-6:** очередь ограничена `max_deferred_tasks`; есть приоритеты; есть максимальная задержка, после которой задача выполняется принудительно (защита от starvation); при переполнении срабатывает аварийный режим (дроп по приоритету + предупреждение в лог с cooldown, а не бесконечный рост памяти). Критические задачи не откладываются никогда.

**Ограничение v1:** планировщик обслуживает **только** задачи, зарегистрированные через `TickPilotApi`. Перехват произвольных `Runnable` из Minecraft запрещён.

### FR-7. Зоны активности
`ActivityZones` определяет режим объекта по расстоянию до ближайшего игрока.

| Зона | Условие | Поведение |
|---|---|---|
| FULL | dist ≤ `full_radius` (32) | Без изменений, полный тик |
| REDUCED | `full_radius` < dist ≤ `reduced_radius` (96) | Разрешено разрежение только для allowlisted типов |
| FROZEN | dist > `reduced_radius` | Разрешено максимальное разрежение только для allowlisted типов |

**AC-7:** если в мире нет игроков — объекты **не** замораживаются автоматически (иначе ломаются фермы и chunk loaders). Есть исключения: force-loaded чанки, объекты из denylist, всё, что помечено как критическое через API.

### FR-8. EntityPolicy (осторожно)
**AC-8:** в v1 по умолчанию — только диагностика. Throttling AI применяется исключительно к типам из allowlist и никогда не меняет частоту полного `Entity.tick()` там, где это может сломать физику, коллизии, езду, поводок, следование за игроком или логику мода. Если безопасный hook не найден — оставить только метрики (INV-4).

### FR-9. BlockEntityPolicy (осторожно)
**AC-9:** по умолчанию — профилирование. Адаптивное обновление только для явных allowlisted типов. Поддерживаются исключения по mod ID и по block entity ID.

### FR-10. ChunkBudget
**AC-10:** ограничивается количество **необязательных** chunk operations за тик. Приоритет: (1) чанк нужен игроку, (2) телепортация игрока, (3) force-loaded, (4) генерация вдали от игроков, (5) фоновые задачи. Игрок никогда не «залипает» в загрузке мира из-за TickPilot; есть аварийный fallback — при подозрении на блокировку лимит снимается.

### FR-11. Adaptive modes
| Режим | Смысл |
|---|---|
| STRICT | Только измерения. Никакого вмешательства вообще. Режим совместимости. |
| BALANCED | Дефолт. Вмешательство только для allowlisted типов и только при HIGH/CRITICAL. |
| AGGRESSIVE | Более раннее и сильное разрежение, всё ещё в рамках allowlist. Требует явного включения. |

**AC-11:** режим меняется командой и конфигом; смена применяется без перезапуска; STRICT гарантированно отключает все политики.

### FR-12. Команды

| Команда | Права | Описание |
|---|---|---|
| `/tickpilot status` | 0 (настраивается) | TPS, MSPT avg/p95/p99/max, режим, load level, deferred tasks, overhead мода |
| `/tickpilot top` | 2 | Сводка по категориям |
| `/tickpilot top entities` | 2 | Top-N дорогих типов сущностей |
| `/tickpilot top blockentities` | 2 | Top-N дорогих типов block entities |
| `/tickpilot profile <seconds>` | 2 | Запуск сессии профилирования (1–300 с) |
| `/tickpilot profile stop` | 2 | Остановка сессии |
| `/tickpilot mode <strict\|balanced\|aggressive>` | 2 | Смена режима |
| `/tickpilot reload` | 2 | Перечитать конфиг |
| `/tickpilot explain` | 2 | Человекочитаемый разбор просадки |

**AC-12:** неверные аргументы дают понятное сообщение, а не исключение; все команды работают в одиночном мире; используется Brigadier + `CommandRegistrationCallback` из Fabric API; тексты — через `Text`/translation keys, не через конкатенацию строк в чат.

### FR-13. `/tickpilot explain`
**AC-13:** вывод содержит: TPS; avg MSPT; p95; p99; самый долгий тик и когда он был; главную категорию нагрузки с долей в %; top-3 entity types; top-3 block entity types; top mod IDs; количество отложенных задач; текущий режим и load level; **одну конкретную рекомендацию** и честную оценку эффекта («ожидаемый эффект неизвестен» — допустимый ответ). Формулировки без обещаний магии.

### FR-14. Публичный API
Пакет `com.tickpilot.api` — стабильная поверхность для других модов.

```java
TickPilotApi.registerTaskProfile(ResourceLocation id, TaskProfile profile);
TickPilotApi.submit(ResourceLocation taskId, Runnable mainThreadWork);
TickPilotApi.registerPolicy(ResourceLocation id, ThrottlePolicy policy);
TickPilotApi.markSafeToDefer(ResourceLocation typeId, long maxDelayTicks);
TickPilotApi.markSafeForAsyncCompute(ResourceLocation typeId);
TickPilotApi.metrics();   // read-only snapshot
```

`TaskProfile` описывает: `deferrable`, `maxDelayTicks`, `critical`, `asyncComputeAllowed`, `coalescable`, `priority`.

**AC-14:** API не требует от потребителя зависимости на внутренние классы; всё публичное имеет Javadoc; при отсутствии TickPilot вызывающий мод не падает (soft dependency, пример в README).

### FR-15. Конфигурация
Формат: TOML (человекочитаемый, с комментариями). Файл: `config/tickpilot.toml`, создаётся автоматически со значениями по умолчанию.

```toml
# --- Бюджет тика ---
target_mspt = 40.0
critical_mspt = 50.0
reserve_mspt = 10.0

# --- Зоны активности ---
full_radius = 32
reduced_radius = 96
min_entity_update_interval_ticks = 1
min_block_entity_update_interval_ticks = 1

# --- Планировщик ---
enable_adaptive_mode = true
default_mode = "BALANCED"
max_deferred_tasks = 10000
max_chunk_operations_per_tick = 8

# --- Профилирование ---
profile_buffer_size = 1200
log_slow_operations_above_ms = 2.0
sampling_enabled = false

# --- Окружение ---
singleplayer_enabled = true
client_hud_enabled = false
integrated_server_optimizations = true
safe_compatibility_mode = false   # true = принудительный STRICT

[lists]
excluded_entity_ids = []
excluded_block_entity_ids = []
excluded_mod_ids = []
throttle_allowlist = []           # только эти типы могут быть разрежены
throttle_denylist = []            # эти не трогаются никогда, приоритет выше allowlist
```

**AC-15:** битый конфиг не роняет сервер — логируется ошибка, применяются дефолты, файл не перезаписывается молча; `/tickpilot reload` перечитывает и валидирует; невалидные значения (например `critical_mspt < target_mspt`) отклоняются с понятным сообщением.

### FR-16. Логирование
**AC-16:** нет логов каждый тик. Логируются: переходы load level; сводка по медленным тикам с cooldown (например не чаще 1 раза в 30 с); ошибки Mixin; невозможность загрузить конфиг; автоматическое отключение небезопасной оптимизации; старт/стоп сессии профилирования.

## 6. Требования к окружению: dedicated + singleplayer

### FR-17. Двойной режим работы
- **Dedicated server:** мод ставится на сервер, работает без клиентского мода, все команды доступны операторам.
- **Singleplayer:** мод ставится в `.minecraft/mods`, серверная часть автоматически поднимается на integrated server, команды работают в одиночном мире.

### FR-18. Разделение сторон
- `main` entrypoint — только server/common логика.
- `client` entrypoint — только HUD, клиентские команды, настройки.
- **Запрещено** упоминать `Minecraft` (клиентский класс-синглтон) в common/server-классах (ни импорта, ни ссылки).
- **Запрещено** загружать client-only классы на dedicated server.
- Серверные Mixins должны работать и на integrated, и на dedicated server (`"environment": "*"` для server-миксинов, отдельный `tickpilot.client.mixins.json` с `"environment": "client"`).
- TPS/MSPT измеряются встроенным сервером, а не рендером и не клиентским FPS.

### FR-19. Жизненный цикл
Подписка на: `ServerLifecycleEvents.SERVER_STARTED`, `SERVER_STOPPING`, `SERVER_STOPPED`.

**AC-19:**
- Состояние создаётся на `SERVER_STARTED` и привязано к конкретному `MinecraftServer` (map или поле через Mixin/accessor, но **не** глобальный singleton, переживающий мир).
- На `SERVER_STOPPING`/`SERVER_STOPPED` останавливаются все executor services, чистятся очереди, сбрасываются метрики.
- Переход из одного одиночного мира в другой полностью сбрасывает состояние (проверяется тестом/ручным сценарием: зашёл в мир A → вышел → зашёл в мир B → метрики начинаются с нуля).
- Если integrated server отсутствует (главное меню), клиентский HUD ничего не делает и не бросает исключений.

### FR-20. Клиентский HUD (опционально, последний по приоритету)
Только для операторов/одиночной игры: TPS, MSPT, текущий режим, число отложенных задач, главный источник нагрузки. Выключен по умолчанию (`client_hud_enabled = false`). Отсутствие HUD не влияет на серверную функциональность.

## 7. Требования к Mixins

- MX-1. Минимальное количество Mixins. Сначала искать событие Fabric API, потом Mixin.
- MX-2. Каждый Mixin имеет Javadoc-комментарий: **куда** внедряется, **зачем**, **какие риски совместимости**, **почему нельзя безопаснее**.
- MX-3. Никаких `@Overwrite` **и никаких `@Redirect`** (расширено на Фазе 4→5, журнал §13 запись #12). Только `@Inject` / `@ModifyVariable` / `@WrapOperation` (MixinExtras) с минимальной областью.
- MX-4. Никакого глобального Mixin, подменяющего тик-систему.
- MX-5. Если target не сопоставляется с mappings 1.21.1 — **остановиться**, проверить mappings (linkie / mappings.dev / `./gradlew genSources`), и только потом продолжать. Не «подгонять» имя наугад.
- MX-6. refmap настроен корректно; `tickpilot.mixins.json` и `tickpilot.client.mixins.json` разделены по environment.

## 8. Требования к тестам

### Unit (JUnit 5, без запуска Minecraft)
- расчёт avg MSPT и TPS из ring buffer;
- p95 и p99 (включая граничные случаи: пустой буфер, 1 элемент, все одинаковые);
- определение `LoadLevel` + гистерезис (не дребезжит на границе);
- выбор `ActivityZone` по расстоянию, включая «нет игроков в мире»;
- приоритеты scheduler и порядок выполнения;
- принудительное выполнение по истечении max delay (защита от starvation);
- поведение при переполнении очереди;
- парсинг конфига: дефолты, битый файл, невалидные значения, round-trip сохранения.

### Интеграционный сценарий (ручной чек-лист + `runServer`)
- dedicated server стартует без других модов;
- все команды выполняются без исключений;
- `/tickpilot reload` работает;
- сервер корректно останавливается, потоки не висят;
- одиночный мир: вход, команды, выход, вход в другой мир — состояние сброшено.

**Важно:** тесты нельзя удалять или ослаблять, чтобы «прошла сборка».
